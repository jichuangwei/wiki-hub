## 从写好一篇文章，到完成一次交付

让 AI 定期整理资讯，很容易先把注意力放在选题和写作上。真正接入网站发布与邮件发送之后，工作会延伸到工具连接、身份授权、版本管理、部署验证和失败恢复。任何一环缺失，都可能出现“文章已经生成，读者却没有收到”的情况。

这次实践最有价值的收获，是把内容自动化拆成几段职责明确、结果可核验的工作。模型负责查资料、分析和组织内容；外部服务负责保存成果、执行发布并记录进度。这样才能在任务结束、会话切换或工具暂时不可用之后，继续完成同一次交付。

## 完整流程怎样衔接

一次定时运行可以分为六个阶段：

1. **准备与检索**：确定本期时间范围，读取统一的写作规则和模板，查找并核实原始资料。
2. **生成与校验**：筛选资讯、形成分析、生成完整 HTML，再检查日期、来源、分类与结构。
3. **提交发布请求**：通过 MCP 调用发布服务，保存这份内容并取得可查询的任务记录。
4. **归档与部署**：发布服务触发 GitHub Actions，由工作流校验内容、提交归档、构建页面并部署。
5. **线上核验**：查看本次工作流结果，访问目标页面，确认线上正文与本次归档一致。
6. **发送邮件**：使用同一份已确认的内容发送邮件，保存邮件服务返回的结果，并单独记录发送状态。

每一阶段都要留下可供下一阶段使用的结果。生成完成需要完整正文，归档完成需要提交记录，部署完成需要本次部署结果，邮件发送需要邮件服务的响应。任务报告也应逐项区分这些状态。

## 各个工具承担什么工作

| 工具或服务 | 在流程中的职责 | 实践中要关注的边界 |
| --- | --- | --- |
| 云任务 | 定时启动、检索资料、生成内容、调用可用工具并整理结果 | 定时运行环境实际能使用哪些连接，需要单独验证 |
| MCP | 将发布、查询等服务能力提供给模型调用 | 工具是否可见、参数定义是否匹配、是否已经授权 |
| Railway | 托管发布服务，使云任务能够访问远程服务 | 服务是否健康、实际运行的版本、日志与持久化能力 |
| Auth0 | 处理登录与身份授权 | 调用方能否登录，以及是否获准访问发布服务 |
| GitHub App | 为服务提供受控的 GitHub 操作身份 | 权限应与所需操作相符，凭据由服务端管理 |
| GitHub Actions | 执行归档、校验、构建与部署工作 | 本次运行是否完成，各步骤有没有失败 |
| GitHub Pages | 承载静态网站，供读者访问 | 页面是否能访问，正文是否已经更新 |
| Gmail 或其他邮件工具 | 发送最终内容并返回发送结果 | HTML、收件人、BCC 支持情况以及重复发送问题 |

Railway 管理服务部署，Auth0 管理身份，MCP 提供工具调用方式，三者需要分别验证。Railway 的部署记录可以帮助判断运行版本；Auth0 的连接则关联应用与用户身份来源。[Railway 部署文档](https://docs.railway.com/deployments)、[Auth0 身份连接文档](https://auth0.com/docs/authenticate/identity-providers)。

## 工具可用性，要在实际运行环境验证

一个会话能够看到发布工具，不能据此推断另一个会话或定时任务也拥有相同能力。本地环境、网页会话、云任务之间，连接与文件的可用范围可能不同。需要在目标运行环境先完成一次小规模验证，确认规则能读取、工具能发现、授权能使用、状态能查询。

共享的写作规则也应放在云任务能够稳定读取的位置。只修改本地文件，或者在某次聊天里更新了要求，未必会影响下一次定时运行。[ChatGPT 定时任务官方说明](https://learn.chatgpt.com/docs/automations)。

排查时可以沿着“连接是否存在、工具是否可见、参数是否正确、调用是否成功”的顺序推进。每一步都依赖不同证据，反复修改写作要求通常解决不了工具连接缺失的问题。

## 身份授权需要分层理解

登录成功之后，仍需确认客户端是否获准访问目标服务，以及服务端是否正确校验了调用身份。一次接入过程会涉及客户端注册、用户登录、资源授权和令牌验证；这些步骤分别决定“谁在调用”与“允许做什么”。[OpenAI 远程工具认证文档](https://developers.openai.com/plugins/build/auth)。

Auth0 负责登录和授权流程，具体的发布能力仍由 MCP 服务实现。排查授权错误时，应结合身份服务日志判断失败发生在哪一层，避免把所有问题都归到账号密码上。

服务连接成功以后，还要检查客户端实际拿到的工具定义。发布服务代码已经更新、远程服务已经运行新版、当前会话已经发现新版参数，是三个不同的验证点。只确认其中一个，后续调用仍可能失败。

## 把生成成果保存下来，才能可靠恢复

长任务经历等待、重试或会话切换后，可能只剩下“正文已校验通过”的摘要，完整 HTML 却没有保留下来。此时重新生成会产生新的内容，无法保证它与原先准备发布的版本一致。

因此，完整正文应作为独立成果保存，并与发布记录关联。恢复时先找回原内容和已完成的阶段，再决定继续执行还是重新生成。内容摘要可以帮助校验一致性，但摘要和字符数无法代替原始正文。

同样的原则适用于发布进度。请求已经受理、归档已经提交、网站已经部署、线上已经核验、邮件已经发送，都应单独记录。一个长时间运行的任务有了这些记录，才有明确的恢复起点。

## 重试与更新，应有不同处理方式

重复执行定时任务是正常情况：用户可能手动补跑，网络可能超时，服务也可能暂时失败。设计时应让相同内容的重复请求能够复用已有结果，避免重复提交和重复发送。

如果同一周期已经存在另一版正文，就需要进一步判断：前一次只是提交失败，还是内容已经公开发布。修复未完成的请求和修改已经上线的文章，对读者的影响不同，应保留不同的审核与版本记录。

邮件也要独立处理重复执行。页面已经上线但邮件尚未发送时，可以从发送阶段恢复；邮件工具返回超时、结果不明时，则应先查发送记录。仅凭任务最后一句话判断是否发过邮件，容易造成重复投递。

## 上线和邮件，都需要各自的验证

工作流显示成功之后，还应访问线上页面。构建、部署和读者实际看到的内容之间可能存在等待时间，也可能出现标题、样式或路径问题。核验时既要看页面能否打开，也要看文章日期、标题、栏目和正文是否对应本次内容。

邮件应复用已经确认的正文，减少网站版和邮件版之间的差异。发送前核实工具是否支持所需的 HTML 与 BCC 功能；发送后记录邮件服务返回的标识。服务接受发送请求并不等于收件人已经阅读，也不保证邮件一定进入收件箱。

收件人信息应由发送环节管理。邮件地址和 BCC 列表混入公开正文，会让内容发布与隐私管理相互耦合，也增加后续维护成本。

## 发布可靠性与内容质量要分别检查

自动化链路跑通，说明内容可以交付；它不能保证资料准确、分类合理或分析有价值。内容校验还需要核对事件日期、一手来源、证据强弱，以及栏目之间的边界。

写作规则和模板也要各司其职。规则决定选题、分类与分析要求，模板负责页面结构和展示。分类错误应先检查规则与素材归属，排版错误应检查模板与渲染。两者分别维护、一起校验，能减少把内容问题误当成部署故障的情况。

## 从一次成功走向持续运行

更容易验证的实施顺序，是先连接并查询工具，再完成一次小规模发布，随后验证线上内容与邮件，最后放进定时任务中观察实际运行。还应测试一次重复执行和一次失败恢复，确认不会重复发布、不会丢失正文，也不会重复发信。

长期维护需要关注三个方面：内容规则是否仍能稳定读取，连接与授权是否有效，远程服务与客户端工具定义是否一致。每次修改其中一部分，都在实际定时运行环境验证完整流程，才能知道改动是否真正生效。

这套实践适用于资讯周报，也适用于研究摘要、团队简报与其他定期内容。它的核心经验是把生成成果、执行能力和结果证据连接起来，让每次交付都能追溯，并在中断后继续完成。
